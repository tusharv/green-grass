# CV updates through chat

Approved workflow: an owner chats on an application page, reviews a proposed change, then applies it to the source CV and reassesses the current application. Publishing the refreshed employer snapshot is optional and unchecked by default.

## Boundaries

- The assistant can ask questions, add/remove skills, and add, replace or remove bullets on an existing work role. It may propose a summary update. Employer, title, employment dates, education, contact and total professional years are immutable in this first release.
- GitHub does not automatically establish Git. Ask about actual use. College practice is not employment experience and does not increase years_experience. An unassigned work claim requires clarification.
- Every proposed edit references an exact excerpt from a human message. New skills must occur as a whole phrase in those excerpts. New numbers must occur in cited messages. The UI shows old/new values and citations, with explicit confirmation that the proposed facts are accurate. User-confirmed edits become source facts; existing rewrite and gap grounding still runs against that source.
- Never accept client-submitted replacement profiles or let model output set readiness. Only server-stored proposals can be applied.

## Storage and consistency

A new CvConversation table, keyed to CV, stores bounded messages, the pending proposal, a revision and updated time. Sharing one conversation per CV serializes changes originating from different application pages. Messages label their application context. Existing tables require no new columns; create_all creates the new table. Delete with its CV.

Each request carries a conversation revision. Proposals carry a random id, source-profile fingerprint and application/job fingerprint. After slow model work, an atomic revision comparison rejects stale requests. Apply uses one database transaction for source profile, fit result, fresh result/plan, conversation and optional share snapshot. Model or database failures leave the old CV/assessment intact. Preserve current design settings. Clear old learning plans and regenerate from current gaps. Original extracted upload text stays unchanged.

Other application assessments stay as snapshots. Their chat sees the latest source CV. Any obsolete proposal must be regenerated. Shared profile text changes only on explicit selection. No chat or source-message content is returned by public endpoints.

## UI and API

The existing Result page contains an Update my CV panel with chat messages, example prompts, input, send progress/error, before/after edits, citations, accuracy confirmation and Apply & reassess. Missing-skill rows can point to this panel. Messages render as plain escaped text.

GET /api/applications/{id}/chat reads state. POST adds a message and produces a clarification or proposed edits. POST /chat/apply accepts proposal id, revision, explicit confirmation and optional shared-profile refresh. DELETE /chat/proposal dismisses a pending proposal. All writes require CSRF and ownership. Bounds: 3,000 characters per message, 40 turns retained, 10 edits per proposal, 4,000 characters per replacement, 100,000 characters per profile. Network/model errors stay inline without losing the typed message.

## Verification

ScriptedModel tests cover follow-up questions; grounded proposals; invented evidence/skills/numbers; unchanged source until apply; work/college separation; successful reassessment; ready/gap/PDF transitions; source/design/share preservation; model failure rollback; stale/replayed proposals; ownership/CSRF; and deletion. Frontend build/tests and browser checks verify accessible chat, clear review controls, and responsive layout. Never call the live model from automated tests.
